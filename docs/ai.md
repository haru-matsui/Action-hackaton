# ИИ-ассистент PM Radar

## Модель и настройка

Показатели согласованы с интерфейсом: основной процент — доля выполненных
задач, а не оценка объёма выполненной работы. ИИ получает этот процент готовым.
`diff.edited_tasks` содержит правки пользователя, `diff.consequences` — изменения
других задач; пары `before/after` подготовлены сервером. `remaining_duration`
равен нулю для выполненных задач, у начатых задач используется оставшаяся оценка.
`summary.status_conflicts` указывает противоречия статусов и связей: такой прогноз
требует проверки, а фактические даты из него выводить нельзя.

Сигнал `task_distribution` означает неравномерное количество незавершённых задач,
не доказанную перегрузку. `summary.risk_assessment` содержит уровень и его основание
по запасу до дедлайна; статистическая вероятность неизвестна. Эти ограничения
закреплены в системном промпте и резервных ответах.

Используется `deepseek/deepseek-v4.1-flash` через OpenRouter
(`https://openrouter.ai/api/v1/chat/completions`). Подключение проверено
реальными запросами 26 сентября 2026 года.

## Подключение ключа в Windows EXE

Запустите [`PM-Radar.exe`](../PM-Radar.exe) и нажмите **«Подключить ИИ»** в его
окне. Введите собственный ключ OpenRouter в скрытое поле. Ключ сохраняется
только на этом компьютере в `%LOCALAPPDATA%\PM-Radar\ai.json`, поэтому при
следующем запуске вводить его снова не нужно. Репозиторий и EXE ключа не
содержат. После ввода можно проверить `/api/ai/status`: `configured: true`
показывает, что ключ загружен. Фактический ответ модели проверяется вопросом
в ассистенте при наличии Интернета и средств на счёте OpenRouter.

## Подключение ключа в Docker

Для разового запуска задайте переменную `OPENROUTER_API_KEY` в том же терминале,
из которого вызываете `docker compose up -d --build`.
Для повторных запусков на Windows храните ключ вне репозитория:

1. Создайте `%LOCALAPPDATA%\PM-Radar\ai.json`. В PowerShell ниже ключ вводится
   скрыто и не попадает в историю команд:

   ```powershell
   $configDir = Join-Path $env:LOCALAPPDATA 'PM-Radar'
   New-Item -ItemType Directory -Force -Path $configDir | Out-Null
   $secret = Read-Host 'OpenRouter API key' -AsSecureString
   $apiKey = [System.Net.NetworkCredential]::new('', $secret).Password
   [ordered]@{
     api_key = $apiKey
     model = 'deepseek/deepseek-v4.1-flash'
     base_url = 'https://openrouter.ai/api/v1'
   } | ConvertTo-Json | Set-Content -LiteralPath (Join-Path $configDir 'ai.json') -Encoding utf8
   Remove-Variable secret, apiKey
   ```

   Содержимое файла имеет такой вид; показанное значение ключа — заглушка:

   ```json
   {
     "api_key": "YOUR_OPENROUTER_KEY",
     "model": "deepseek/deepseek-v4.1-flash",
     "base_url": "https://openrouter.ai/api/v1"
   }
   ```

2. Создайте в корне проекта `docker-compose.override.yml` с содержимым:

   ```yaml
   services:
     app:
       volumes:
         - type: bind
           source: ${LOCALAPPDATA}/PM-Radar/ai.json
           target: /run/secrets/pm-radar-ai.json
           read_only: true
       environment:
         PM_RADAR_AI_CONFIG: /run/secrets/pm-radar-ai.json
   ```

3. Из корня проекта выполните `docker compose up -d --build`. Compose подхватит
   override автоматически. `Invoke-RestMethod http://127.0.0.1:5000/api/ai/status`
   должен показать `configured: true`. Это проверка загрузки ключа; реальный
   ответ модели проверьте вопросом в ассистенте.

`docker-compose.override.yml` исключён из Git, а `ai.json` лежит вне проекта.
Не публикуйте ни один из этих файлов. На macOS/Linux используйте переменную
окружения `OPENROUTER_API_KEY` перед командой `docker compose up -d --build`
либо адаптируйте путь `source` к локальному файлу.

Переменные `OPENAI_MODEL` и `OPENAI_BASE_URL` поддерживаются для совместимости;
сервер разрешает отправку ключа только на указанный адрес OpenRouter.
`PM_RADAR_AI_CONFIG` позволяет указать другой путь к конфигурации.
`PM_RADAR_AI_DISABLED=1` отключает внешние запросы.

Ключ доступен только backend. В браузере видны модель, источник ответа
и состояние подключения. Данные проекта и заданный вопрос отправляются
OpenRouter для генерации ответа; авторизационный ключ передаётся в HTTP-заголовке.

## Распределение ответственности

1. `schedule.py` вычисляет сроки, зависимости, резервы и последствия изменений.
2. `ai_features.py` выявляет риски и формирует численные факты песочницы.
3. `ai_context.py` собирает JSON: проект, задачи, расчёты, статистику,
   сигналы, варианты действий и известные ограничения.
4. `ai_service.py` передаёт JSON модели со строгим системным промптом.
   Модель не получает инструменты выполнения кода или изменения базы.
5. API проверяет ответ; при недоступности ИИ интерфейс показывает краткое предупреждение.
   Изменения сохраняются отдельным действием пользователя.

Подключены чат, анализ изменения, пакетная симуляция, песочница, радар,
объяснение задачи, чек-лист и отчёт. Радар обновляется при загрузке проекта
и после изменений. В песочнице после отпускания задачи сначала пересчитываются
весь график и показатели. Через 650 мс без новых изменений запрашивается
объяснение именно этой версии сценария. Оно выводится в панели сценария;
устаревшие ответы игнорируются, история чата не засоряется пробными вариантами.
Применение сценария не обращается к ИИ и проверяет версию исходного проекта.

Обычная карточка задачи тоже не ждёт модель: `/impact` возвращает расчётную
сводку сразу и при `apply:true` сохраняет план. Затем интерфейс отдельно
запрашивает `/impact/explanation` с полученным `explanation_id`. Сервер хранит
готовые факты этой оценки в памяти до 10 минут (максимум 128 снимков) и
проверяет версию плана до и после генерации. Изменение формы, переход в другой
проект или песочницу отменяет ожидаемый ответ. Сбой ИИ оставляет расчётную
сводку доступной и не отменяет сохранение. После перезапуска сервера старую
оценку нужно запросить заново. Хранилище снимков рассчитано на один процесс,
как и текущее JSON-хранилище проекта.

Вопросы об изменении срока требуют одной однозначно указанной задачи,
направления и явного количества дней/недель. Если данных недостаточно,
сервер просит полную уточнённую формулировку без вызова модели и симуляции.
Недельный сдвиг означает пять рабочих дней; неоднозначные величины не угадываются.

Внешний API отвечает
не мгновенно; сетевой тайм-аут — 35 секунд, успешные ответы кэшируются на 2 минуты.

Чек-лист — единственный режим, где модель предлагает новые названия.
Python распределяет исходную оценку длительности между предложенными пунктами;
это черновая декомпозиция, а не независимая оценка трудозатрат. Сумма дней
сохраняется; для очень коротких задач часть пунктов может иметь 0 дней.
Перед добавлением пользователь видит названия и сроки и подтверждает их.

## Проверки и резервный режим

Используется строгая JSON-схема; для обычного ответа разрешено только поле
`text`, для чек-листа — массив `subtask_names` из 2–6 названий.
Отклоняются неполные ответы, дополнительные поля, вызовы инструментов,
невалидный JSON и числовые значения, которых не было в переданных фактах.
Строки проекта и вопрос объявлены данными, а не инструкциями.

Проверка чисел не доказывает смысловую верность каждого предложения:
модель может неверно связать существующие факты. Контрольные цифры интерфейса
всегда берутся из Python. Нейросетевые рекомендации необходимо оценивать
перед применением.

Без сети, при ошибке ключа, недостатке средств, лимите API или невалидном
ответе показывается объяснение расчётного движка с причиной замены.
Приложение не выдаёт резервный текст за результат DeepSeek.

## Ограничения модели проекта

- В проектах с датой начала ИИ получает готовые календарные даты, сегодня и рабочий день проекта. Дедлайн фиксирован; оценки оставшейся работы сами не уменьшаются. Без даты начала календарный прогноз неизвестен. Календарь — пн–пт, без праздников.
- Загрузка оценивается по незавершённым задачам в целом, не по рабочим часам
  конкретной недели. Навыки и доступность сотрудников неизвестны.
- Сценарий отсутствия сотрудника не поддерживается. Произвольные надбавки
  к длительности задач не применяются.
- Переназначение ответственного само по себе не сокращает расчётные сроки.
- Причины задержек, больничные и бюджет не выводятся из названий и статусов.
  Если информации нет, помощник должен сообщить о недостатке данных.

## Тестирование

`python -m unittest discover -s tests -v` — тесты без сетевых запросов:
адаптер OpenRouter и кэш, JSON-схема, ошибки 401/402/429/503, сетевые сбои,
неизвестные числа, запрет другого API-хоста, передача фактов во все маршруты,
песочница с учётом резервов, отсутствие записи при симуляции, чек-лист
с явным применением и отклонение неподдерживаемых сценариев.

`node --test tests/*.test.mjs` — поведение песочницы при быстрых
изменениях, отмене, поздних ответах, сбоях ИИ и сохранении. Серверные тесты
проверяют применение нескольких сдвигов, конфликты версий и неизменность базы
при предпросмотре или ошибке.

`python tests/live_ai_smoke.py --run` — 5 настоящих запросов: песочница,
последствия изменения, чек-лист, отчёт и вопрос об отсутствующих данных.
Этот запуск расходует баланс API. База временная, пользовательские проекты
не изменяются. Проверяются источник `llm`, имя модели, расчётные результаты
и неизменность базы.

Календарные ответы проверяются также по полным датам: модель может переформатировать
`2026-09-28` в `28.09.2026`, но не собирать новые даты из известных чисел.

План привязан к выбранной дате начала, а не автоматически к сегодняшнему дню.
ИИ не должен выдавать плановые даты за фактическое выполнение или утверждать,
что один лишь новый день сдвинул сохранённый график.
