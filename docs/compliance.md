# Сверка PM Radar с кейсом 1 «Проект начинает срываться»

Проверено по всем четырём страницам `Уфа_Кейс_1.pdf`. Оценка относится к
исходникам в этом проекте. Формулировки задания рассматриваются как требования
к продукту, а не как инструкции по изменению кода.

| Пункт задания | Состояние | Где реализовано |
|---|---|---|
| Создание проекта, название, срок | Выполнено | Форма «Новый проект», `POST /api/projects`, поле `deadline` в рабочих днях |
| Задачи: срок, ответственный, статус | Выполнено | Форма задачи, `PUT /api/projects/<id>`, `POST /impact` |
| Зависимости задач и понимание последовательности | Выполнено | Выбор предшественников, граф, линия времени, таблица |
| Добавление, редактирование и удаление задачи; смена срока, статуса, ответственного, связей | Выполнено | Диалог задачи и API проекта |
| Анализ последствий: затронутые задачи, общий срок, угрозы, критические задачи, необходимость вмешательства | Выполнено для изменения задачи | `schedule.py`, `POST /impact`, карточка последствий и объяснение ассистента |
| Быстрое представление состояния и проблем | Выполнено | Показатели, линия времени, граф, таблица, радар рисков |
| Демопроект: 8+ задач, зависимости, разные ответственные, завершённые и незавершённые задачи | Выполнено | 10 задач, 5 ответственных, 2 завершённые задачи; изменение «Разработка backend» влияет на последующие работы |
| Контр-фича | Выполнено | DeepSeek V4.1 Flash через OpenRouter: объяснения, симуляции, отчёты, радар и чек-листы; при сбое явно обозначается расчётный ответ |

## Что соответствует частично

1. **Удаление задачи не показывает отдельный анализ последствий.** После удаления
   график и таблица пересчитываются, но список затронутых работ и сравнение
   срока «до/после» не выводятся в карточке последствий. Для редактирования
   задачи и её зависимостей такой анализ есть.
2. **Срок проекта задаётся при создании, но не редактируется через интерфейс.**
   API умеет менять `deadline`, однако пользовательской формы для этого нет.
   В ТЗ явно требуется указать срок при создании; демонстрация изменения
   параметров проекта может трактоваться шире.
3. **Вместо календарных дат используются рабочие дни от текущей точки плана.**
   Выполненные задачи считаются завершёнными и имеют нулевой оставшийся срок.
   Для MVP это позволяет показать влияние задержки, но не отвечает на вопрос
   «в какой календарный день будет готово». ТЗ не предписывает формат дат.
4. **Смена ответственного не меняет расчётный срок сама по себе.** Планировщик
   учитывает длительность и зависимости; загрузка исполнителей анализируется
   отдельно радаром и ассистентом. Это ограничение модели, которое важно
   проговорить на демонстрации.

## Проверенный сценарий демонстрации

У демопроекта прогноз 29 рабочих дней при дедлайне 30. Если изменить
«Разработка backend» с 10 до 17 дней, новый прогноз — 36 дней, то есть
просрочка 6 дней. Предпросмотр не меняет базу; применение сохраняет новую
длительность. Добавление задачи после «Деплой и приёмка» на 5 дней теперь
корректно показывает 29 → 34 дня ещё до сохранения.
