# PM Radar — инструмент управления рисками и изменениями в проекте

Работающий MVP для руководителя проекта: создаёте проект с задачами, сроками,
ответственными и зависимостями — а система на лету пересчитывает график и
показывает **последствия любых изменений**: что сдвинется, вышел ли проект за
дедлайн, какие задачи под угрозой и что делать.

Главный вопрос продукта: **«Если сейчас что-то изменится, что произойдёт с
проектом и на что мне обратить внимание?»**

## Запуск проекта с нуля

**Самый быстрый запуск на Windows:** установите Docker Desktop один раз и дважды нажмите
[`START-Docker.bat`](START-Docker.bat). Скрипт соберёт контейнер, дождётся ответа
сервера и откроет браузер; если Docker Desktop закрыт, скрипт запустит его сам.
Для настоящих ответов DeepSeek используйте
[`START-With-AI.bat`](START-With-AI.bat): он скрыто запросит OpenRouter ключ.
Ключ нужен свой или выданный отдельно для проверки; в репозитории его нет.

### 1. Подготовьте окружение

- Установите **Docker Desktop** на Windows или macOS. На Windows BAT сам
  запустит установленный Docker Desktop; при первом запуске может понадобиться
  закончить его первоначальную настройку. На Linux нужны Docker Engine и плагин
  Docker Compose v2.
- Убедитесь, что порт `5000` свободен. Интернет нужен для первой загрузки образа
  Python и установки зависимостей; для ответов DeepSeek он нужен постоянно.
- Python и Node.js для обычного запуска не требуются: сервер и интерфейс входят в
  Docker-образ. Git нужен только если вы клонируете репозиторий.

В PowerShell проверьте Docker:

```powershell
docker compose version
docker info --format '{{.ServerVersion}}'
```

Если запускаете проект вручную и Docker Engine ещё не готов, вторая команда
выдаст ошибку — дождитесь Docker Desktop. BAT ждёт готовности автоматически.
На macOS/Linux те же команды выполняются в терминале.

### 2. Получите проект и перейдите в его папку

```powershell
git clone https://github.com/haru-matsui/Action-hackaton.git
Set-Location .\Action-hackaton
```

Если проект скачан ZIP-архивом, распакуйте его и откройте в терминале папку с
`docker-compose.yml`. Все команды ниже выполняются из неё. На Windows вместо
команд следующего шага можно использовать `.bat` из начала инструкции.

### 3. Соберите и запустите приложение

```powershell
docker compose up -d --build
docker compose ps
Invoke-RestMethod http://127.0.0.1:5000/api/health
```

В ответе последней команды должно быть `ok: true`. Первая сборка может занять
несколько минут. Затем откройте [http://127.0.0.1:5000](http://127.0.0.1:5000).
Контейнер слушает только `127.0.0.1`, поэтому приложение доступно на этом
компьютере. Оба Windows-скрипта запускают Docker Desktop при необходимости и
ждут готовности сервера перед открытием браузера.

При первом запуске загружается демо-проект **«Запуск CRM-платформы»**: 10 задач,
несколько зависимостей и 5 ответственных. Его начало — 22.09.2026, дедлайн —
03.11.2026. Если `data/db.json` уже существует, приложение открывает сохранённые
проекты и не заменяет их демо-данными.

Для проверки основного сценария откройте задачу «Разработка backend», измените
длительность с 10 до 17 рабочих дней, нажмите «Оценить последствия», затем
«Сохранить». До сохранения результат является предпросмотром.

### 4. Подключите ИИ, если нужны ответы DeepSeek

Без ключа планирование и интерфейс работают; ассистент явно показывает
расчётный ответ вместо ответа модели. На Windows проще всего дважды нажать
`START-With-AI.bat` и ввести ключ в скрытом запросе. Если запускали проект
вручную, тот же результат дают команды PowerShell:

```powershell
$secret = Read-Host 'OpenRouter API key' -AsSecureString
$env:OPENROUTER_API_KEY = [System.Net.NetworkCredential]::new('', $secret).Password
docker compose up -d --force-recreate
Remove-Item Env:OPENROUTER_API_KEY
```

После закрытия терминала ключ нужно вводить снова при следующем пересоздании
контейнера. Для постоянной локальной настройки через файл `ai.json` используйте
[инструкцию по ИИ](docs/ai.md#подключение-ключа-в-docker). Не добавляйте ключ,
`ai.json` или `docker-compose.override.yml` в Git. Проверить, видит ли сервер
ключ, можно командой `Invoke-RestMethod http://127.0.0.1:5000/api/ai/status`:
`configured: true` означает, что ключ загружен; фактическую связь с моделью
проверяйте запросом к ассистенту.

### 5. Работа с данными и управление контейнером

| Действие | Команда из папки проекта |
| --- | --- |
| Обновить код и пересобрать | `docker compose up -d --build` |
| Посмотреть состояние | `docker compose ps` |
| Посмотреть ошибки сервера | `docker compose logs --tail=100 app` |
| Следить за журналом | `docker compose logs -f app` |
| Остановить приложение | `docker compose down` |

Изменяемая база находится в `data/db.json` рядом с `docker-compose.yml` и
сохраняется после `docker compose down` и пересборки. Исходный шаблон демо —
`backend/data/db.json`; он не заменяет существующую базу. Папка `data/`
исключена из Git. Если раньше использовалась Windows-версия, **до первого
запуска** скопируйте `%LOCALAPPDATA%\PM-Radar\data\db.json` в `data/db.json`.
Перед переносом на другой компьютер скопируйте собственный `data/db.json`
отдельно от репозитория.

Если браузер показывает старый интерфейс после обновления, нажмите `Ctrl+F5`.
Если порт `5000` занят, измените в `docker-compose.yml` левую часть строки
`127.0.0.1:5000:5000`, например на `127.0.0.1:5001:5000`, пересоберите
контейнер и откройте `http://127.0.0.1:5001`. При ошибке сборки или запуска
проверьте `docker compose ps` и `docker compose logs --tail=100 app`.

### Доступ для жюри

Во время очного показа запустите `START-With-AI.bat` на своём компьютере и
откройте локальный адрес в браузере. Если жюри запускает код у себя, для
реального DeepSeek им нужен собственный или отдельно предоставленный ключ
OpenRouter. Двойной клик по `START-Docker.bat` запускает весь проект с явно
обозначенным резервным ответом ассистента. Ключ автора отсутствует в Git;
одна только ссылка на GitHub не предоставляет доступ к работающему ИИ.

Для удалённого просмотра нужна отдельная публикация приложения на сервере:
текущий Docker Compose открывает порт только на `127.0.0.1`. На сервере ключ
задаётся в настройках окружения, а жюри получает адрес приложения. Перед
публикацией нужно ограничить доступ к серверу: текущий MVP не содержит учётных
записей, и открытые API позволят посетителям видеть проекты и расходовать
баланс ключа. Не добавляйте ключ в репозиторий и не открывайте локальный порт
напрямую в Интернет.

## Что реализовано

1. **Создание проекта** — название, дата начала, календарный дедлайн, задачи со
   сроком, ответственным и статусом (к выполнению / в работе / выполнено).
2. **Связи между задачами** — зависимости «B после A», задаются чекбоксами в
   форме задачи; цикл в графе отклоняется с понятной ошибкой.
3. **Управление проектом** — добавление/редактирование/удаление задач, смена
   сроков, статусов, ответственных и зависимостей.
4. **Анализ последствий изменений** — движок CPM (ранний/поздний старт,
   резерв времени, критический путь). Любое изменение сначала проходит через
   **предпросмотр последствий**: какие последующие задачи сдвинутся и на
   сколько, изменился ли общий срок, нарушен ли дедлайн, какие задачи под
   угрозой, требуется ли вмешательство.
5. **Представление проекта** — показатели проекта и три связанных представления:
   линия времени с датами и отметкой «Сегодня», таблица с расчётными резервами и SVG-граф
   зависимостей. Критический путь выделен фиолетовым, риски — янтарным,
   завершённые задачи — зелёным. При равных критических ветках выделяются
   все их задачи и связи; параллельные задачи не объединяются в одну цепочку.

## Контр-фича: ИИ-ассистент руководителя проектов

Встроенный чат-ассистент **не считает сам** — он получает готовые результаты
CPM-движка и симуляций и переводит их на человеческий язык:

- **объясняет последствия** каждого применённого изменения (авто-комментарий
  в чате после применения правки задачи);
- **предлагает решения**: переназначить ответственного (видит, что один
  сотрудник ведёт несколько критических задач), разбить задачу на подзадачи,
  согласовать сдвиг дедлайна;
- **отвечает на вопросы «что будет, если…»** в режиме симуляции:
  «что будет если Тестирование задержится на две недели?».
  Сценарий ничего не сохраняет; изменения принимаются пользователем.
- **формирует краткие отчёты**: «дай отчёт по проекту» — статус, готовность,
  выполненные/незавершённые задачи, критический путь, угрозы, вывод о
  необходимости вмешательства.

Подключена **DeepSeek V4.1 Flash через OpenRouter**
(`deepseek/deepseek-v4.1-flash`). Ключ читается сервером из локального файла
`%LOCALAPPDATA%\PM-Radar\ai.json` или переменной `OPENROUTER_API_KEY`.
Он не передаётся браузеру и не включается в Docker-образ. На другом компьютере ключ
нужно настроить отдельно. Нейросеть получает JSON с готовыми расчётами;
у неё нет инструментов записи в проект. Ответы проверяются по схеме и числам.
При ошибке API приложение показывает расчётный ответ с явной отметкой о замене.
В каждом ответе виден его источник. Подробности и ограничения —
[`docs/ai.md`](docs/ai.md).

## Демонстрация основного сценария (2 минуты)

1. Открываете демо-проект: начало 22.09.2026, дедлайн 03.11.2026. При текущих
   оценках срок по плану — 30.10.2026 (29 рабочих дней), на 2 рабочих дня раньше дедлайна.
   Критический путь подсвечен фиолетовым.
2. Кликаете «Разработка backend» → меняете длительность 10 → 17 →
   **«Оценить последствия»**: система показывает +7 дн. по всем
   последующим задачам, превышение дедлайна на 5 дн., список задач под угрозой
   и рекомендации. Изменение ещё НЕ применено.
3. **«Сохранить»** → график перерисовывается, ассистент в чате пишет
   объяснение своими словами.
4. В чате: «Что будет, если Тестирование задержится на 3 дня?» → симуляция
   без изменения сохранённого плана.
5. «Дай отчёт по проекту» → сводка и вердикт «требуется вмешательство».
6. Меню «⋯» в верхнем правом углу → «Восстановить демо» возвращает исходное
   состояние выбранного проекта для повтора.

### Как устроен фронтенд

HTML задаёт оболочку, навигацию и диалоги. `app.js` загружает проект через
`api.js`, хранит состояние экрана и передаёт данные в `views.js` для отрисовки.
`ui.js` содержит общие элементы оформления и экранирование пользовательского
текста. Расчёт сроков остаётся в Python: фронтенд показывает результаты API.

На широком экране ассистент находится справа от плана. На узком — под ним,
Ассистент открывается кнопкой сверху справа и сворачивается крестиком;
без него план занимает всю ширину. График, таблица и зависимости переключаются
вкладками; последствия редактирования показываются прямо в форме задачи.
В песочнице можно сдвинуть несколько ещё не начатых задач мышью или клавишами
← и →. Длительности и дедлайн сохраняются. После отпускания полосы Python
пересчитывает весь сценарий; график, таблица, зависимости и показатели показывают
результат, исходные положения полос отмечены пунктиром.
Переход в таблицу или зависимости выключает песочницу с подтверждением сброса
несохранённых изменений.

ИИ запрашивается через 650 мс после готовности расчёта, если новых изменений нет.
Во время перетаскивания запросов нет. Новое изменение, сброс и выход прекращают
ожидание старого ответа; он не попадёт в интерфейс или чат. Уже отправленный
запрос к провайдеру может завершиться на сервере, но его результат игнорируется.
Пояснение появляется в панели сценария справа (на узком экране — под планом).

«Применить сценарий» сохраняет все сдвиги одной операцией, не ожидая ИИ.
Сервер сверяет версию проекта и отпечаток рассчитанного сценария. При изменении
проекта в другой вкладке сохранение блокируется до обновления. Выход и сброс
возвращают исходный план. При незаданном дедлайне риск его нарушения не оценивается.

## Проверка

### Как читать сроки

В новых проектах задаются дата начала и календарный дедлайн (необязательно).
В существующем проекте нажмите «Указать даты» под названием: старые данные
не получают выдуманную дату начала. До выбора даты сохраняется прежняя шкала
рабочих дней. Сроки можно изменить кнопкой «Изменить даты».

Под названием видны дата начала, сегодня и текущий рабочий день проекта.
По выходным показано число прошедших рабочих дней; до начала — соответствующий статус.
Линия времени, таблица, прогноз, песочница и ассистент используют одни серверные даты.
Шкала Ганта пропускает субботу и воскресенье; один шаг перетаскивания — один рабочий день.
Дедлайн включителен: задача длительностью 1 день, начатая в пятницу, заканчивается
в пятницу; длительностью 2 дня — в понедельник. Праздники не учитываются.

Календарный план привязан к выбранной дате начала. Перенос начала пересчитывает
даты задач и срок по плану, сохраняя фиксированный дедлайн. Наступление нового дня
обновляет отметку «Сегодня» и номер рабочего дня, но не сдвигает план автоматически.
Оценки автоматически не уменьшаются: обновляйте их по мере выполнения.

При создании и переносе проекта начало не может быть раньше сегодняшнего дня.
Уже сохранённая историческая дата допускается без изменения (например, при правке
только дедлайна). Демо по запросу пользователя имеет фиксированные начальные даты
22.09.2026 — 03.11.2026; они восстанавливаются вместе с демо.

Даты вводятся обычным текстом `ДД.ММ.ГГГГ`, без посимвольной маски. Поддерживаются
вставка ISO-даты и восемь цифр без разделителей; форматирование происходит после
выхода из поля. Рядом доступен календарь. Проверка дат выполняется также на сервере.
Открытая страница проверяет день раз в минуту и при возвращении в окно; открытая
форма/песочница не сбрасывается. Вчерашние сценарии требуют обновления плана.

Часовой пояс по умолчанию — `Asia/Yekaterinburg`; для другого окружения задайте
`PM_RADAR_TIMEZONE` в Docker Compose. Календарный расчёт: `backend/planning_calendar.py`.
Фактические даты начала и завершения задач не записаны, поэтому выполненные задачи
показаны без выдуманных исторических дат. Нулевая задача на границе завершения
предшественника относится к дате его окончания; отдельная нулевая задача — к дате
планирования. Она тоже не может выполнить уже прошедший дедлайн.
У задачи «К выполнению» указана оценка предстоящей работы, у задачи «В работе» —
оценка оставшегося времени. У выполненной задачи сохранена введённая оценка,
но оставшаяся длительность равна нулю. Таблица показывает именно остаток.
Расчётные позиции графа не являются историческими датами выполнения задач.
Выполненные задачи не входят в критический путь оставшейся работы.

Если начатая или выполненная задача зависит от незавершённой, интерфейс и радар
показывают противоречие. Статусы не исправляются автоматически; расчёт следует
заданным зависимостям, и такой прогноз требует проверки пользователем.

### Показатели и сравнение изменений

Основной процент — число выполненных задач, делённое на общее число задач,
с округлением до целого. Это один показатель в интерфейсе, отчёте и фактах ИИ.
Демо: 2 из 10 = 20%. Оценки длительности не используются для процента готовности.

В оценке последствий отдельно показаны правки пользователя и изменения других
задач после пересчёта. Даже если общий срок остался прежним, видны пары
«было → стало» для оценки, начала, окончания, резерва, статуса, ответственного
и связей. Смена исполнителя не меняет срок без изменения оценки.
Отсутствие новых угроз не снимает ранее выявленные проблемы.

Радар сравнивает количество незавершённых задач всего проекта. При трёх и более
задачах у одного человека и разнице минимум в две задачи он предлагает проверить
распределение. Это не доказательство перегрузки: часы, навыки и доступность неизвестны.

Уровень риска в песочнице определяется запасом до дедлайна: превышение — высокий,
нулевой запас — средний, 1–2 рабочих дня — умеренный, больший запас — низкий.
Это правила продукта, а не вероятность срыва. Без дедлайна уровень не определяется.
Отметка задачи «Под угрозой» означает незавершённую критическую задачу при
нулевом резерве либо запасе проекта до дедлайна не более двух дней.

### Автоматические проверки

После установки `backend/requirements.txt` запустите
`python -m unittest discover -s tests -v`. Проверка покрывает загрузку
интерфейса, демоданные, предпросмотр изменения и добавления задачи, а также
сохранение после применения. Тесты ИИ проверяют JSON-контракт, ошибки ключа,
баланса и сети, отбрасывание неизвестных чисел, сохранность базы при симуляции
и создание подзадач только после подтверждения. Они не обращаются к сети.
`node --test tests/*.test.mjs` проверяет быстрые повторные изменения,
задержанные ответы, сброс, конфликты, ошибки сети и применение без ожидания ИИ.
Для отдельной проверки реального подключения:
`python tests/live_ai_smoke.py --run` (5 запросов, расходует баланс OpenRouter,
использует временную демонстрационную базу).
